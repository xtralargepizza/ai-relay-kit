# Complex Relay

Use for several independent deliverables, a large partitionable batch, or different workflows that must converge into one checked result. Invocation: “Use Complex Relay for <task>.” This selects the protocol; new user-owned chats still require an explicit request to create/use new chats. Reuse existing authorized Sol chats when suitable. Do not launch a team merely to document this workflow.

## Size the team to executable work

| Job structure | Starting arrangement |
| --- | --- |
| Small known-route correction | One Sol worker with focused self-checks; normal Relay |
| One substantial dependent deliverable | One Sol worker and one Sol reviewer; normal Relay |
| Independent items using one established process | One Sol monitor/reviewer and initially two Sol workers, each owning disjoint batches |
| Several genuinely different workflows | One Sol coordinating monitor, workers grouped by workflow; add a dedicated Sol reviewer for a stream only if specialist checks or review backlog justify it |
| New shared prerequisite blocks all outputs | One owner proves the smallest usable prerequisite; others perform independent preparation, then consume the same released result |

These are starting arrangements, not fixed maximums. Expand only within authorized scope and available agent/chat capacity when there is ready independent work and the bottleneck can benefit. More idle agents do not accelerate a serial prerequisite, saturated renderer, provider limit or review backlog. Retire finished workers; do not keep a standing fleet running.

## Models and communication

- Astra supplies a brief initial decision/engineering packet only when needed, reusing previous accepted decisions. It does not perform the working, review or recovery loop.
- GPT-6.1 Sol workers normally use medium reasoning. The coordinating reviewer uses GPT-6.1 Sol xhigh for this user's Complex Relay mode. Additional reviewers remain Sol; select effort for the actual decision rather than using xhigh for routine formatting or copying.
- The Sol monitor owns worker dispatch, direct defect feedback, checkpoint recovery and finite completion. Give all participants its exact verified ID and the human authorization source for cross-chat coordination.
- After handoff, work must be owned by the Sol host or its agents. Astra-owned local agents can wake Astra and cannot necessarily be steered from another chat; checkpoint and transfer them safely before relying on final-only routing.
- Workers report only to their Sol reviewer/monitor. Reviewers communicate with workers directly. The monitor alone sends one final consolidated reviewed outcome to the initiating Astra chat. No startup messages, first-batch notices, retry reports, forwarding requests, capacity warnings or routine escalations to Astra.
- Keep genuine unresolved decisions in the monitoring chat with evidence and a precise question. If no authorized route remains, return an honest final blocked/partial outcome with completed work preserved. Do not invent approval or suppress an approval required for the actual action.

## Dispatch once, then work from evidence

Apply SKILL.md's result-first execution contract. On an unproven shared route, the first batch is one complete representative deliverable, not one intermediate per worker. Keep parallel preparation useful while a named owner resolves the common dependency. Count repeated shared failures across all shards; changing a shard or item ID does not start a new retry allowance. After the first complete result passes, scale the verified route.

Keep one lightweight manifest in the task folder, reusing existing status files. Record:

- Workstream/batch ID, stable input identities, dependency and ready state.
- Verified owner/chat/model, reviewer, exclusive output paths and any active claim.
- Next concrete artifact/checkpoint; actual progress and provider/job receipts.
- Separate counts for prepared, intermediate, completed and reviewed items; first completed-result evidence and elapsed time when measured.
- Acceptance evidence, defects, correction status and final output identity.
- Global resource limits and the sole integration owner.

Partition by source identity or another non-overlapping key and balance by estimated effort, not simply file count. A workstream owns its outputs; it must not rewrite another stream or shared source masters. Lock shared cache mutations and serialize shared interactive applications. More chats must not multiply the global CPU/GPU/render/API budget. Record any user-approved spending limit; do not manufacture one. A coordinator's conservative execution checkpoint may limit initial fan-out, but must be labeled as its own choice and reconsidered within existing authorization instead of becoming a fictitious user approval barrier.

Release a shared prerequisite immediately after its required focused checks pass. Do not make other workers rebuild it, repeat its smoke test, or wait for optional documentation. Render/review the first small useful batch before scaling an unfamiliar route.

At every artifact/review handoff, release the next executable item to an available worker. A case-specific correction remains with its owner and does not lock the whole queue. If a defect may affect the shared route, identify which subsequent stages actually depend on it and keep independent preparation/execution moving; do not approve affected results prematurely. Avoid both idle workers behind unrelated polishing and uncontrolled multiplication of a shared failure.

## Stringent review with low overhead

Reviewers are accountable for both correctness and efficient execution:

1. Inspect actual output/evidence, including required identity, fit, coverage, seam or data checks for that domain. File existence, metadata and reassuring worker prose are not substitutes.
2. Return pass, or an exact defect, one concrete next action and its acceptance condition. Complete the correction loop; do not merely log defects and leave them for Astra.
3. Recheck changed evidence and dependencies affected by that change. Reuse unchanged passing checks; preserve accepted artwork/data. Avoid duplicate screenshots, recrawls, full log reads and independent reimplementation.
4. Use launch-failure, job-submitted, artifact-ready and completed-batch events with compact status cursors. Failures must reach the Sol monitor immediately, before unrelated exploration. During uncertain launch/setup use a short checkpoint (normally about two minutes); inspect the last relevant command once if it is missed, and issue an exact recovery action. After confirmed provider submission, wait against its actual expected latency/completion event. Apply the active execution-supervision contract in SKILL.md; do not wait for a final batch to discover a broken invocation. Time targets do not waive correctness or justify killing valid in-flight work.
5. After two failures of the same approach, stop repeating it. Use an established alternative when supported; isolate a novel prerequisite or document the exact blocker. Capacity errors permit a bounded retry from saved state, not a retry storm or an unapproved model switch.

When review is the bottleneck, reduce batch size or assign an authorized Sol reviewer to a disjoint stream. When compute or provider capacity is the bottleneck, reduce concurrency. Add workers only when they can shorten the remaining critical path without duplicate work.

## Recovery, integration and stop

Keep job receipts and checkpoints so transient errors do not restart completed work. Before moving a batch, verify its original writer stopped or released the claim and account for live processes. Resume from the last verified artifact. Never steal a live claim or launch duplicate paid jobs.

One integration owner merges accepted outputs and updates the shared index/Brain when in scope. Reconcile every assigned item as accepted, specifically unresolved, or blocked; counts must balance and unknowns remain explicit. Run cross-stream compatibility checks after merge where necessary.

The final packet contains deliverable links, actual coverage/counts, reviewers and model dispatch, corrections verified, remaining limitations and measured timing if available. Distinguish provider time from total elapsed time. Stop after the requested deliverable passes or no authorized progress remains. This protocol is not a background scheduler, automatic model switch, guaranteed speedup or enforced token budget.
